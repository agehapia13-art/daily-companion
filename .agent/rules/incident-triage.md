# 不具合申告時の多層切り分けルール（Incident Triage）

ユーザーから「〇〇できない」「反映されない」「動かない」などの不具合・異常の申告を受けた際、単一の推測（クライアントキャッシュや操作ミスなど）に飛びついて案内してはならない。

## 切り分けの4レイヤー（上から順に実測確認）

1. **配信・インフラ層**: そもそも最新の成果物が稼働・配信されているか（デプロイ状態、実配信URLへの疎通・内容確認）
2. **サーバー・データ層**: API応答、権限、データ構造、永続化状態に異常や不整合がないか
3. **ビルド・コード層**: ソースコードとビルド成果物の整合性、構文、スコープ、参照先に誤りがないか
4. **クライアント・環境層**: 端末側のキャッシュ、ローカル状態、ネットワーク、入力に起因していないか

## 行動原則

- ユーザーへ環境依存の対処（リロード・設定変更等）を促す前に、**AI側で実測・検証可能な層（1〜3）を先に確認**する。
- 確認後も原因が特定しきれない、または複数要因が考えられる場合は、1つに決めつけず **考えられる複数の可能性と確認結果を並列で提示** する。
